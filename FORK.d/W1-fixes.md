Mutation-proven: moving the increment after the compare makes the test see both guesses evaluated. | No. |

A person who already exists signs in again with no invite. `bootstrapUserSpace` accepts a transaction client so the atomic path can include it. Offline test covers: no invite refuses by name and writes no user; a valid invite creates exactly one account, spends the invite once (a second phone is refused `already_redeemed`), and a returning person needs none. | No. |

## Decisions (for FORK.md "Decisions taken while building")

| Decision | Reason | Date |
|---|---|---|
| The canonical phone form is digits without a leading `+` | The webhook's sender (the `wa_id`) is the shape the fork never controls; normalising a caller's `+`-prefixed value down to it means every entry point lands on one hash. Normalising the other way would invent a `+` the provider never sends. `normaliseIdentifier` in `identity.ts` is the one place this is decided; `requirePhoneValue` validates the digits it leaves. Changing the hash input is safe now because no production identity hashes exist under the old form (Wave 1 is not deployed). | 2026-11-17 |
| The invite hash rides on the pending sign-in row, not in the browser's verify call | The token the welcome page held must survive the WhatsApp round trip without a second door or a new code table; the row already carries per-door state. Only the hash is stored, so a database read cannot mint a link, the same property the invitations table keeps. | 2026-11-17 |
| Person creation went through the transaction, not the auth internal adapter | The invite claim must commit or roll back with the person it admits, and Better Auth's internal adapter cannot join a caller's transaction. The adapter applies no user-create hooks in this repo's auth config (only account and session hooks), so `tx.user.create` writes the same row the adapter would, and the session itself is still issued through the auth layer's `issueSession`. | 2026-11-17 |
| `SIGNUPS_ENABLED` continues to govern the email door only | The phone door's admission is owned by the invitations service unconditionally, so there is one rule to reason about; a deployment that wants open phone admission invites nobody and the door stays closed by default (no row, no person). | 2026-11-17 |
