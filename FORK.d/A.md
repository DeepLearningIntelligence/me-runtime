# Packet A: brand

The product is "me.io". The name's single authority on web is `apps/web/src/me/brand.ts`
(`BRAND_NAME`); email templates in `packages/auth` and API copy carry it as a literal because the
API cannot import from the web app. An upstream `APP_NAME`/`appName` setting would retire the
literals; upstream hard-codes the name in `packages/auth` today.

Each row below is one patch: file, reason, whether an upstream configuration could replace it.

## Findings the lead should know

1. **Stale `packages/i18n/locales/messages.pot` poisons every build.** The pot is a gitignored
   artifact; `lingui compile` (CLI and the vite plugin) merges it into every compiled catalog, so a
   checkout that ever ran `intl:extract` ships old strings in built JS until the pot is deleted. It
   carried the old mobile strings into the web bundle on this checkout. Deleted here; a fresh
   extraction regenerates it from current source. Consider an upstream guard (compile ignoring the
   template, or CI deleting it before build).
2. **`env.ts` leaves `EMAIL_FROM` to the deployment.** No in-repo default says Rakazo, so the From
   line is correct as soon as the host sets `EMAIL_FROM="me.io <...>"` (owner item, W0.3).
3. **`apps/www` was left untouched.** The Astro marketing site does not ship with the product (the
   demo serves `apps/web` on one origin), so its Rakazo copy is out of scope. Desktop and Electron
   locale files likewise stay (not shipped).
4. **The dev bundle carries internal `rakazo*` identifiers** (storage keys, `data-rakazo-*`
   attributes, CSS class names, `x-rakazo-*` headers, `rakazoScreen`, `__rakazo_custom_model__`).
   None renders as text a person can read. Renaming them would break saved state and cross-process
   contracts for no visible gain.
