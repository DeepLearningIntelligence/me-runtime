# Packet P11 (ME-RUN-004): phone sign-in fixes (2026-11-18)

Written from the live test on `me.gofunditnow.com` (18 November): a correct code
was consumed by a 403 `invite_required`, so the retry said `code_invalid`; an
expired `ME-` code got silence; and the wa.me link may never open WhatsApp in
in-app browsers. Six fixes, one branch (`me-p11-signin-fixes`), one commit each.

## What changed, per fix

- **F1, the live bug.** `verify` in `apps/api/src/me/phone-signin/service.ts` no
  longer consumes the code. It charges the attempt (conditional update, before
  the compare, unchanged) and compares in constant time, then returns the phone,
  the row's invite hash, and the code's one redemption. The redemption runs
  inside the admission transaction: `signInVerifiedPhone` calls it first inside
  the same transaction that creates the person and claims the invite, so a
  refusal (`invite_required`, or an invite the invitations service cannot claim)
  rolls the consume back and the code stays usable; a returning person, or a
  racer joining a concurrent winner, redeems right before the session, where the
  conditional update still makes it single use. Design choice: the packet's
  transactional option, because the pre-check option would need the door to
  re-implement the invitations service's validity rules (by hash) to also
  protect `invite_invalid`, and one rule must have one implementation. Attempts
  still count: the charge precedes the compare exactly as before.
- **F2.** `user.phoneHash` (nullable, unique) is the one attachment a phone can
  have: the generated migration `20261118095000_me_user_phone_hash` adds it.
  Phone sign-in resolves the linked account by hash first, then the derived id a
  phone-created person has always carried; a phone-created person now carries
  the hash from birth. `linkVerifiedPhone` (new, `session.ts`) attaches a
  verified phone to a signed-in person in the same transaction as the
  redemption, refusing `already_bound` (409) when another person holds the phone
  (linked or phone-created, the latter caught by the derived id) or the person
  already carries a different phone; the unique constraint is the concurrency
  backstop and the loser is refused by name. The owner bootstrap
  (`apps/api/src/cli/bootstrap-owner.ts`) accepts `OWNER_PHONE`, validates it
  with the door's one canonical check (`requirePhoneValue`, now exported),
  hashes it with `hashIdentifier` under `ME_IDENTITY_HASH_KEY`, and writes only
  the hash; a malformed value fails with a named error before any write, and a
  phone another account holds is refused by name. `POST /api/auth/phone/start`
  and `/verify` accept `link: true`, which requires a session (401 `unauthorized`
  otherwise, checked before the code is looked at).
- **F3.** `doorRefusal` (new, `apps/web/src/me/onboarding/door.ts`) folds the
  door's refusals: an `invite_required` or `invite_invalid` refusal is sticky for
  the door that produced it, so a later `code_invalid` from the same nonce
  cannot push the real reason, and the ask-for-a-link next step, off the screen.
  A new door or Start over clears it. The email link for existing owners is the
  "Sign in with email" control the Auth page renders directly under the panel
  (`Auth.tsx` is outside this packet's file list; the copy and the sticky
  message are in the listed files).
- **F4.** `handleInbound` answers an unknown nonce and an expired one with the
  same text (`EXPIRED_CODE_REPLY`), so the sender learns nothing beyond "that
  code is dead" and the 04:12:53 silence is gone. The provider message id claim
  (same transaction) keeps a Meta replay silent. `InboundOutcome` lost
  `nonce_unknown` and `code_expired` from its silent reasons; the other silent
  reasons (`replayed`, `already_bound`, `phone_mismatch`, `identity_key_missing`)
  stay silent on purpose: answering them would tell a stranger that a nonce
  exists.
- **F5.** The start response carries `businessNumber` (the configured
  `WHATSAPP_BUSINESS_NUMBER`, never hardcoded); the door shows the `ME-` code in
  large text under the WhatsApp button with a labelled Copy button
  (`aria-label="Copy sign-in code"`, keyboard reachable, the button's visible
  focus state) and the line "Or send this code on WhatsApp to <number>". No
  clipboard access keeps the button on Copy; the code stays on screen to send by
  hand.
- **F6.** Every wa.me link in the onboarding flow navigates in the same tab
  (phone-signin's Open WhatsApp, flow's Open WhatsApp, Back to WhatsApp, and
  Chat in WhatsApp; the packet named the first three, the fourth is the same
  kind of link), because in-app browsers drop new-tab navigations. The open door
  is kept in session storage (`me.phone-door`, like the entry flag), so the
  reload on the way back lands on the code field with the nonce still in hand;
  an expired door loads as no door at all.

## The legacy derived-id lookup (kept, with its removal date)

Two reads in `apps/api/src/me/phone-signin/session.ts` resolve a phone by the
derived id (`phoneUserId(phoneHash)`): the sign-in resolution's second read
(`signInVerifiedPhone`, after the `phoneHash` lookup misses) and the link flow's
legacy guard (`linkVerifiedPhone`, refusing a link onto a phone a phone-created
person already owns). Both exist for one reason: people created by phone
sign-in before `user.phoneHash` shipped (migration `20261118095000`) have a
row whose id is the derived id and whose `phoneHash` is null. The derived id is
a pure function of the hash, so the read can never name a second person for one
phone; deleting it would strand every such person (their sign-in would read as
"no account", the exact F1 bug shape for them). Whether any such rows exist on
the host is UNVERIFIED, so the reads stay.

**Removal date: 2027-06-01**, or earlier, once this check on the host returns
zero rows (run by the owner after any deploy that includes this packet):

```sql
SELECT count(*) FROM "user"
WHERE phone_hash IS NULL AND id LIKE '%-phone';
```

Every phone-created row carries the `-phone` id suffix, so a zero there means
the derived-id reads have no readers left and both can go in the same commit.

## Decisions

| Decision | Reason | Date |
|---|---|---|
| F1 uses the transactional design, not the pre-flight one | The pre-flight would need a by-hash invite validity check inside the door, a second implementation of the invitations service's admission rule; the transaction gets `invite_required` and `invite_invalid` both from the one admission path, and the attempt charge is untouched either way. | 2026-11-18 |
| `user.phoneHash` is the attachment, not a second table | The packet says one authority and no second code table; a nullable unique column on the person keeps one lookup (`findUnique({ where: { phoneHash } })`) and the derived id stays the stable id a phone-created person already carries. Old releases keep working: the column is additive, old code never reads it. | 2026-11-18 |
| The expired and the unknown nonce get the same words | The packet forbids revealing whether a nonce ever existed beyond expired versus not recognised; one constant, `EXPIRED_CODE_REPLY`, is that line. | 2026-11-18 |
| The link flow's UI entry is `/sign-in?link=1` | The packet's file list has no settings page; `PhoneDoorPanel` reads the flag and starts a link door. A visible entry point in the portal would need files outside the packet (question for the reviewer). | 2026-11-18 |
