# Packet P12 (ME-RUN-004b): link authority on the verify route (2026-11-18)

One change, one branch (`me-p12-link-authority`): `POST /api/auth/phone/verify`
(`apps/api/src/me/phone-signin/routes.ts`) now derives its mode from the code's
pending row, never from the request. The request-driven branch is deleted; there
is no second path.

## What changed

- After `verify()` succeeds, `verified.linkUserId` (the row's `linkUserId`,
  written at `/start`) decides:
  - **Row has `linkUserId`:** the link branch. The request's session is read;
    no session is refused 401 `unauthorized`; a signed-in person other than
    `row.linkUserId` is refused 403 `session_mismatch` by the guard already in
    `linkVerifiedPhone` (`session.ts`, unchanged); the matching person completes
    the attach and answers `{ ok: true, linked: true }`.
  - **Row has `linkUserId` null:** the plain sign-in branch. A request
    carrying `link: true` is refused 400 `link_not_started` and nothing is
    attached (no session issued, no `phoneHash` written, code unconsumed).
    Otherwise it signs the person in exactly as before.
- Ordering consequence: the mode is knowable only after the row is read, so the
  refusals now come after `verify()`. A refused verify consumed nothing even
  before (the consume rides in the admission, P11 F1), so every refusal here
  still leaves the code usable; a link door's attempt charge for a signed-out
  caller is the one behavioural cost, and it is bounded by the existing
  per-row attempt lockout. `/start` keeps its request-time session check,
  because at start no row exists yet to decide from.

## Enforcement points and tests

New `routes.test.ts` mounts the routes on a Hono app over offline fakes (the
same shape `service.test.ts` and `session.test.ts` use) and asserts the mode
decision end to end:

| Guard | Test | Mutation (named; break, fail, restore byte-identically, pass) |
|---|---|---|
| A link door with no session is 401, nothing attached | `routes.test.ts` "refuses a link door with no session" (401 `unauthorized`, no `phoneHash`, row unconsumed, no session issued) | "401 guard removed": the request fell through to `linkVerifiedPhone` and got 403 instead of 401 |
| A link door redeemed by a different signed-in person is 403, nothing attached | `routes.test.ts` "refuses a link door redeemed by a different signed-in person" (403 `session_mismatch`, no attach, row unconsumed); `session.test.ts` already covers the same guard in `linkVerifiedPhone` directly | "session_mismatch guard removed" (in `session.ts`): the other person got 200 and the attach went through |
| A plain door a request calls a link is 400, nothing attached | `routes.test.ts` "refuses a plain door that a request calls a link" (400 `link_not_started`, no session, no `phoneHash`, row unconsumed) | "link_not_started guard removed": the request fell through to `signInVerifiedPhone` and got 403 `invite_required` instead of the 400 |
| Both modes still complete | `routes.test.ts`: the opener completes their own link door (200 `linked`, hash attached, code consumed); a plain door with no link flag signs a returning person in (200, session cookie set, code consumed) | not a guard; no mutation |

## The legacy derived-id lookup: count pending, reads stay

P11 kept two reads by derived id in `session.ts` until the server is shown to
hold zero legacy rows (people created by phone sign-in before `user.phoneHash`
shipped). This packet could not reach the host, so the count is still UNVERIFIED
and both reads stay untouched. Do not guess it.

Correction to P11's query: the generated migration
`20261118095000_me_user_phone_hash` added a quoted camelCase column, so P11's
unquoted `phone_hash` would fail with "column does not exist". The corrected
query is:

```sql
SELECT count(*) FROM "user" WHERE "phoneHash" IS NULL AND id LIKE '%-phone';
```

Run it on the host (owner item); a zero removes the derived-id reads in the
same commit, on the removal date P11 set (2027-06-01) or earlier.

## Decisions

| Decision | Reason | Date |
|---|---|---|
| The row decides the mode, not the request | The request is the one input a stranger controls; the row is written by `/start` under a session. A request flag that contradicts the row is refused by name instead of honoured. | 2026-11-18 |
| `link_not_started` is a route-level refusal, not a `PhoneSigninFailure` | Only the route reads the request, so only the route can detect the contradiction; the service never sees a mode argument to contradict. The 400 lives beside `session_mismatch`'s entry in `routes.ts`. | 2026-11-18 |
| The web door is untouched | `verifyPhoneDoor` sends only `nonce` and `code` today, so `link_not_started` cannot reach `door.ts`'s copy map; adding the entry now would be copy for a flow nothing sends. If a caller starts sending `link: true` on a plain door, `DoorFailureReason` and `doorFailureText` need the entry then. | 2026-11-18 |
