# P15: base-green fix packet

`me` at `a9fe0cc7a15e` was red on two defects a reviewer found on the base branch
itself. This packet fixes both on `me-p15-base-green`; nothing else merges first.

## Defect 1: `invitations.postgres.test.ts` failed on the base branch

**Diagnosis: test-setup defect, not a code defect.** Reproduced at `a9fe0cc`:

    FAIL ... invitations.postgres.test.ts > concurrent redeem of one invite token
    AssertionError: expected [] to have a length of 1 but got +0
    ...both racers: PrismaClientKnownRequestError P2003
    "Foreign key constraint violated on the constraint: `me_invitations_redeemedByUserId_fkey`"

Both racers died on the foreign key before the compare-and-swap could be
exercised. The claim records the redeemer in `me_invitations.redeemedByUserId`,
a real foreign key to `user` by schema design (`onDelete: SetNull`). The only
production caller, the phone door, claims inside the transaction that creates
the person (`apps/api/src/me/phone-signin/session.ts`), so the key holds there.
The postgres test never created the two redeemer accounts, so both claims
failed. The test had never run with a database: the Wave 1 commit
(`eabe8c782`) shipped it with the API suite "1754 tests, 354 skipped"
(Postgres-dependent, no database on that machine).

**Fix** (`apps/api/src/me/invitations/invitations.postgres.test.ts`): the
`beforeAll` creates the two candidate redeemer accounts next to the inviter and
the `afterAll` removes them (they are not the inviter's cascade). The
assertions are untouched. Proven: the file passes with
`VERIFY_DATABASE=1` against a throwaway database (12/12 tests across the
invitations directory).

**Guard proven by mutation, and where it lives.** Dropping the claim's CAS
predicate (`status: "issued"`) from `invitations.ts` made the postgres test
still pass three runs in a row: on this machine the two racers serialise, so
the loser reads the committed `redeemed` status and refuses with
`already_redeemed` at the status read regardless. The discriminating proof is
the unit suite's interleaved racer test the postgres file itself names as its
guard: with the same mutation, `invitations.test.ts` "a racer whose read
predates another's claim still cannot claim it" fails with
`promise resolved "{ inviterId: 'inviter', ... }" instead of rejecting`; with
the guard restored (diff empty) it passes. Mutation name: "the claim's status
predicate is dropped".

**Also on this file**: `pnpm lint` (biome) was red on base for a pre-existing
unused `BillingEmulator` import and format drift in the same file; cleaned so
the file passes `pnpm lint`. No behaviour change.

## Defect 2: `prisma migrate diff` shows the schema and migrations disagree

**How it was run.** Prisma 7 requires `datasource.shadowDatabaseUrl` in
`prisma.config.ts` to diff a migrations directory (now reads
`SHADOW_DATABASE_URL`), and its shadow replay neither creates
`_prisma_migrations` nor honours pre-seeded state: it wipes every user schema
before replaying, so the RLS migration's
`REVOKE ALL ON TABLE "_prisma_migrations" FROM rakazo_app` fails with `42P01`.
Real deploys are unaffected: `prisma migrate deploy` creates the table before
any migration runs. For diffing, a copy of the migrations directory with one
prepended helper migration that creates `_prisma_migrations` in a side schema
(`migrate_meta`) makes the replay faithful; the copy lives outside the repo.

**Raw diff (migrations vs schema datamodel), before the fix, exit 2:**

    [*] billing_audit_events: column id default changed from
        Some(DbGenerated(Some("(gen_random_uuid())::text"))) to None
    [*] computer_updates, email_sends, model_credit_accounts, model_credit_entries,
        model_credit_lots, push_tokens: foreign key removed and added (same name)
    [*] mcp_servers: renamed index mcp_servers_user_id_slug_idx
        to mcp_servers_userId_slug_idx
    [*] user_action_approval_rules: renamed index
        ..._userId_effect_matchKind_matchValue_k to ..._matchVal_key
    [-] space_model_role_choices: unique index (spaceId, userId, role, provider,
        modelId, credentialId) removed
    [-] user_model_role_choices: unique index (userId, role, provider, modelId,
        credentialId) removed
    [-] vault_credentials: unique index (userId, spaceId, name) removed

**Classification:**

1. **Real: six foreign keys without `ON UPDATE CASCADE`.** They were declared
   inline in their `CREATE TABLE` statements with only `ON DELETE CASCADE`
   (`20261023120000_push_tokens`, `20260908010000_computer_updates`,
   `20261023000000_model_credits`, `20261029120000_marketing_email`), while the
   schema's default referential action and the other 194 constraints in a
   migrated database carry both actions (verified: 194 of 200 with the action).
   `20261218140000_fk_on_update_cascade` re-creates them with
   `ON DELETE CASCADE ON UPDATE CASCADE`; constraint names are unchanged and
   the tables are small, so a deploy overlapping the previous release keeps
   working.
2. **Real: `billing_audit_events.id` default, resolved on the schema side.**
   The database carries a `gen_random_uuid()::text` default the schema did not
   declare, but it is load-bearing: four `SECURITY DEFINER` trigger functions
   (`billing_audit_credit`, `billing_audit_usage`, `billing_audit_lot`,
   `billing_audit_account_closed`, in `20261023000300_billing_audit` and
   `20261023000500_credit_expiration`) insert audit rows without an id and
   rely on it. A first cut of the fix dropped the default and replaced one
   trigger; re-running the credit suites showed the other three break too
   (`organization.deleteMany` in cleanup failed with
   `null value in column "id" of relation "billing_audit_events"`), so
   dropping the default would need rewriting four upstream trigger functions.
   The schema declares the default instead:
   `@default(dbgenerated("(gen_random_uuid())::text"))` on
   `BillingAuditEvent.id`. The one observable change: audit rows written
   through the client (the reconciler's `balance_rebuilt` and the cap
   command's `usage_cap_changed`) get uuid ids from the database instead of
   cuids, the same shape the trigger rows already have; nothing reads the id
   (the reconciler and the cap command aggregate only). The migration carries
   no statement for this column, and `prisma migrate diff` reports it no
   more.
3. **Naming drift only: two index names.** `mcp_servers_user_id_slug_idx` and
   `user_action_approval_rules_userId_effect_matchKind_matchValue_k` were
   created with names from an older canonicalisation (snake_case, and a
   63-byte truncation `matchValue` to `matchVal`). Their definitions match the
   schema exactly; only the names differ from what Prisma 7 canonicalises on
   introspection. A rename migration would be churn with zero functional
   effect, so none was written.
4. **Intentional, not drift to fix: three `NULLS NOT DISTINCT` unique indexes**
   (`space_model_role_choices`, `user_model_role_choices`,
   `vault_credentials`). The Prisma datamodel cannot express
   `NULLS NOT DISTINCT`; the schema documents each as "created in SQL" at the
   model, and the migrations create them
   (`20261025120000_model_connections`, `20261025200000_account_settings`,
   `20261027120000_vault_credentials`). The diff reports them "removed" only
   because the schema side cannot see them. Migrating them away would delete a
   uniqueness guarantee the code relies on.

**After the fix**, the same diff (exit 2) reports only items 3 and 4:

    [*] mcp_servers: renamed index ...
    [*] user_action_approval_rules: renamed index ...
    [-] three documented NULLS NOT DISTINCT unique indexes

The same set is what `prisma migrate diff` reports for a migrated database
against the schema, on both paths below, so nothing expressible remains
undone.

**Both database paths proven** (`prisma migrate deploy`, throwaway local
databases only):

- A, from an empty database: every migration applied including the new one;
  diffing the resulting database against the schema reports exactly the
  irreducible set above.
- B, how production moves: upstream `v0.11.0`'s migrations applied to a second
  empty database, then the fork's `prisma migrate deploy` on the same database
  applied every fork migration including the new one; the same diff result.
  After B: 200 of 200 foreign keys carry `ON UPDATE CASCADE`, and
  `billing_audit_events.id` has no column default.

## How the database suites actually run, and what the base run showed

`pnpm --filter @rakazo/api test` with `VERIFY_DATABASE=1` and one shared
`DATABASE_URL` is not the harness the repo's own CI uses for the database
tests. The runner is `pnpm test:integration`
(`packages/testkit/src/cli/harness.ts`): it takes
`CI_POSTGRES_URL` (here a throwaway local database), runs `pnpm db:migrate`
with `DATABASE_MIGRATION_URL` as the owner and `DATABASE_URL` as a
`rakazo_app` runtime login (so row-level security is enforced as in a
deployment), sets the test environment (`SIGNUPS_ENABLED=true` and the rest
of the harness block), and runs every `*.postgres.test.ts` in apps and
packages with `COPY_TEST_DATABASE=1`, one fresh copy of the migrated database
per file.

Running the api suite against one shared database instead fails on the base
branch itself for environment reasons, which this packet records rather than
fixes:

- `caller-scoping.postgres.test.ts` refuses by name:
  `DATABASE_MIGRATION_URL must name the table owner login` (the file throws
  when the owner and runtime logins are the same).
- `space-availability.postgres.test.ts` and `space-members.postgres.test.ts`
  fail their row-level-security assertions (`expected [...] to not include
  'owner:weekly-review'`): connected as the table owner, RLS is bypassed by
  design, so the tenant isolation those assertions prove cannot be observed.
- `desktop-host-choice.postgres.test.ts` fails on `Registration is closed`:
  the harness sets `SIGNUPS_ENABLED=true`; a bare run does not.
- `cli/model-credit-cap.postgres.test.ts` spawns
  `node --import tsx apps/api/src/cli/model-credit-cap.ts` relative to the
  repo root and fails with `ERR_MODULE_NOT_FOUND` when vitest's cwd is the
  package directory; under the harness (vitest run from the repo root) the
  path resolves.
- With one shared database, failed cleanups also pollute later files: the
  same 10 files that pass alone failed in a shared-database full run, and
  passed again on a fresh database. Per-file copies exist precisely for this.
