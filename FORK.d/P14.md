# P14: WhatsApp is the default (branch `me-p14-whatsapp-default`)

Written 18 November 2026. After a phone sign-in succeeds, the number that sent
the `ME-` message becomes the chat address of the person's default agent, so
their first WhatsApp message afterwards just works. The manual
Settings, People, Connect a chat app step stays for everything the auto-link
refuses to do.

## What changed

### One linking authority

`attachMessagingIdentity(tx, { provider, address, dmThreadId?, installationId?,
userId, spaceId, botId })` in `packages/db/src/messaging.ts` is the one writer of
a person's `MessagingIdentity` rows. It creates on a fresh address, moves the
owner's own address to the requested bot, and refuses an address another person
holds (`other_user`) without writing. `redeemMessagingLinkCode` calls it; the
phone sign-in's auto-link calls the same function. Unique violations are not
caught inside it on purpose: Postgres aborts a transaction whose statement
failed, so the caller re-reads outside the transaction to settle which
constraint lost. `provisionMessagingIdentity` keeps only the synthetic-user
path it already owned (not for this packet).

Enforcement points:
- `attachMessagingIdentity`, `packages/db/src/messaging.ts`: the writes.
- `redeemMessagingLinkCode`: manual path, same function.
- `attachInTransaction`, `apps/api/src/me/phone-signin/session.ts`: auto-link,
  same function; the race settlement reads outside the transaction.

### The sealed sender address

`me_phone_signins.senderAddress` (generated migration
`20261219100000_me_phone_signin_sender_address`, additive) holds the bound
sender's WhatsApp address sealed with `EncryptedSecretStore`, the cipher the
secret store already uses for secrets (`packages/adapters/src/secrets.ts`); no
new cipher was written. The seal's AAD record id is
`me-phone-signin:<row id>`, so a ciphertext copied to another row or deployment
fails authentication. Set when the `ME-` message binds the nonce, opened in
`verify` only after the code compared equal and the door is alive (an expired
door never yields it), cleared by the same write that consumes the code, and
never logged: every log line names the failure, not the number.

The phone sign-in promise "only the hash is stored" holds for everything except
this short-lived sealed field and the `MessagingIdentity` the messaging channel
itself needs to reply.

### The auto-link

`attachWhatsappAfterSignin` (`apps/api/src/me/phone-signin/session.ts`) runs
after the session is issued, for a plain sign-in and for a signed-in link
alike:
- default agent: the oldest non-archived bot the person owns in their first
  space, created with the onboarding first-agent defaults (name "Chief", color
  `#FF781C`, `spawnKey: "onboarding:first"`, empty instructions) when they have
  none;
- state machine, all returned by name: `linked` (fresh attach, welcome queued),
  `already_linked` (their number already chats; nothing is moved or rewritten),
  `linked_elsewhere` (logged, counted), `agent_has_other_number` (the bot keeps
  its other number; the manual path is the way to switch), `not_attempted`;
- welcome: one `messagingOutbound` row ("You're connected. Message me here any
  time.") written in the same transaction as the identity write, keyed
  `signin-welcome:<sha256 of the nonce>` with `skipDuplicates`, delivered by the
  existing `messagingDeliverJob` path;
- no failure can fail the sign-in: the whole step is one try/catch that logs
  and returns `not_attempted`.

`POST /api/auth/phone/verify` answers `{ ok: true, whatsapp: <state> }` (and
`linked: true` beside it on the link path). The config wiring needed two
one-line changes outside the packet's file list, declared below.

### Onboarding and the account menu

- `door.ts`: `verifyPhoneDoor` returns `{ whatsapp: state }`; an older server's
  answer without the field reads as `not_attempted`.
- `phone-signin.tsx` stores the state for the journey (`entry.ts`,
  `me.whatsapp-link` in sessionStorage); a refused verify stores nothing.
- `flow.tsx`: `linked` or `already_linked` skips the manual link step; the done
  screen ends Back to WhatsApp (same tab, `https://wa.me/<business number>`
  through the capabilities URL) whatever opened the journey, and names why a
  number could not link otherwise.
- `SidebarFooter.tsx`: the account menu (the sidebar footer popover) gains a
  WhatsApp row: "Connected · <agent name>" from `rpc.messaging.status`, or
  "Connect" opening Settings, People. The row renders only when the shell
  loaded the status. The bottom-left button is now **Connect tools** (also in
  the keyboard-shortcuts dialog and the command palette, the same command).

## Files outside the packet's list, and why

- `apps/api/src/messaging-runtime.ts`: the sign-in config is built here; it now
  passes `encryptionKey` so the bind can seal the address. One line.
- `apps/api/src/app.ts`: passes `jobs` into `mountPhoneSigninRoutes` so the
  welcome can enqueue its deliver job. One line.
- `apps/web/src/pages/shell/keyboard-shortcuts-dialog.tsx` and
  `use-palette-actions.ts`: the same command's label, renamed with the button.
- `apps/web/e2e/me-whatsapp-default.spec.ts` (new): the Playwright proof.
